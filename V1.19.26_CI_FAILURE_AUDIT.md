# FlyBrain V1.19.26 — CI failure audit / FIX2

Date: 2026-10-06

## Exact failure from supplied CI logs

The V1.19.25_CI_FIX1 validation job reached **Generate runtime maps** successfully. The
canonical FBR-10-OLF2-MOTORROUTE build had already passed:

- 16,669 neurons
- 2,072,633 canonical edges
- 264 retained ORNs
- 53 unique ORN type strings
- 54 retained (type, entryNerve) pairs
- canonical FBR-10 SHA-256:
  `4d643835b7e924ace93fb4b36500a1195d4f8129318da79a5f4df84bb6dc8cda`

The job then failed in `tools/build_sensory_input_map.py` before producing
`sensory_input_map.tsv`.

Exact exception:

```text
pyarrow.lib.ArrowInvalid: Field named name is not found
```

The builder requested a `name` column that is not part of the published MaleCNS v1.0
annotation schema. The verified schema contains `instance`, but no generic `name` field.

This is a **source-schema bug in the runtime-map generator**, not a failure of FBR-10
generation or an Android runtime crash.

## Secondary defect caught before CI

The same V1.19.25 builder referenced `mechanosensory_site(row)` when writing `mechSite`,
but that helper was absent from the actual source file. Therefore, simply removing the
invalid `name` column would have exposed a second failure (`NameError`) immediately
afterwards.

V1.19.26 fixes both defects.

## V1.19.26 correction

`tools/build_sensory_input_map.py` now:

1. Reads only columns actually published by MaleCNS v1.0:
   `bodyId, superclass, type, class, subclass, receptorType, flywireType,
   somaSide, rootSide, entryNerve, instance`.
2. Keeps `side_source()` annotation provenance based on `somaSide`, `rootSide`,
   `instance`, `type`, and `flywireType`; no geometric side inference is introduced.
3. Implements `mechanosensory_site(row)` using published annotation vocabulary only:
   `ANTENNAL`, `LEG`, `WING`, `HALTERE`, `BODY`, or `OTHER`.
4. Leaves unknown vocabulary as `OTHER` rather than inventing an anatomical assignment.
5. Does not modify FBR-10 topology, add neurons, add edges, or inject motor commands.

## What the supplied logs prove

The supplied CI logs prove that the canonical FBR-10 build and the preceding structural
audits passed. They do **not** prove wall-escape behavior because the job stopped while
generating runtime maps, before APK assembly.

The decisive next CI milestone is therefore:

`canonical FBR-10 → sensory maps → FBD105 → Android tests → assembleDebug → APK`

Only after that APK exists can obstacle behavior be evaluated experimentally.
